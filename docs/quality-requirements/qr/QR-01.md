# QR-01: Keep Shared Data And API Keys Confidential

A teacher can read and correct only explicitly shared decks, while learner, teacher, and service API keys remain confidential between those parties.

- **Status:** Active
- **Characteristic:** Security
- **Sub-characteristic:** Confidentiality
- **Business importance:** High
- **Technical risk:** Medium
- **Changed:** 2026-10-24, per [DEC-068](../../decisions.md#dec-068): extend the shared-deck confidentiality check to both participants' keys and the built-in service key.

## Scenario

### Source

A signed-in learner or teacher, through the interface, browser network tools, or direct API requests.

### Stimulus

The teacher asks for a learner's shared or unshared deck, card, or text, or either participant inspects the other participant's or service's API-key data.

### Environment

Normal operation with two separate accounts, a learner owning one shared and one unshared deck, distinct personal keys for learner and teacher, and service-funded generation configured separately, per [DEC-019](../../decisions.md#dec-019) and [DEC-068](../../decisions.md#dec-068).

### Artifact

The frontend's account settings and request paths, the backend's deck, card, text, teaching, and generation endpoints, and every response either account receives.

### Response

The product shall return the shared deck and its cards to the assigned teacher and shall answer requests for the learner's unshared deck, cards, or texts as if they did not exist.

The product shall disclose neither participant's key to the other participant and shall disclose no built-in service key to either account; sharing, viewing, editing, and regeneration shall preserve these boundaries.

### Response Measure

Every deck, card, and text endpoint called with the teacher's session against the learner's unshared items returns `404` in 100% of calls, as required by [TOS-03](../../threshold-of-success.md#tos-03).
Using distinct test keys, account responses, rendered fields, and browser-visible requests contain neither the other participant's key nor the service key in all sharing, viewing, editing, and generation checks.
A participant's personal request may contain their own key when sent to their chosen provider.
