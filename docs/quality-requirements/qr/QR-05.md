# QR-05: Keep The Learner's Work When The LLM Fails

When the LLM provider fails or answers with something that is not cards, the learner sees a message, no broken card is saved, and the marked words stay marked for a retry.

- **Status:** Active
- **Characteristic:** Reliability
- **Sub-characteristic:** Fault Tolerance
- **Business importance:** Medium
- **Technical risk:** Low
- **Changed:** 2026-10-24, per [DEC-050](../../decisions.md#dec-050) and [DEC-073](../../decisions.md#dec-073): bound validation retries to three attempts and report a rejected or expired key immediately.

## Scenario

### Source

The LLM provider, or the gateway in front of it.

### Stimulus

The provider returns an error, times out, rejects the key, or returns an answer that cannot be read as cards.

### Environment

A learner generating or rewriting cards, with the service's key or their own key.

### Artifact

The generate, rewrite, and batch-rewrite actions in the `backend` and the `frontend`.

### Response

The product shall show the learner a message that says the provider failed, shall save no card from the failed request, and shall keep the text, the marks, and the existing cards as they were.

For a sentence that repeatedly fails validation, the product shall make at most three generation attempts, counting the initial attempt, before marking it Failed check and reporting that it could not produce a valid card.
A rejected or expired API key shall be reported as soon as the provider returns that error, without waiting for a batch-quality threshold or retrying the same rejected credentials.

### Response Measure

For each of the four failures, simulated in the backend tests and once against a real provider with a wrong key: the learner gets a message, the number of cards is unchanged, and pressing generate again after the failure is fixed creates the cards.

For three consecutive invalid sentences, exactly three attempts occur and no invalid card is saved; a valid earlier attempt stops retries.
For a rejected or expired key, the first error response produces a visible message and no automatic retry with that key.
The separate degradation warning is specified by [QR-09](QR-09.md), per [DEC-076](../../decisions.md#dec-076).
