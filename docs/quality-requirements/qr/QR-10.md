# QR-10: Diagnose A Failed Request

An operator can locate a failed staging request and its aggregate latency signal.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

A system operator investigating a failed request.

### Stimulus

A staging card-generation request in the learner's core task returns a server error while telemetry is enabled.

### Environment

The deployed staging backend and staging OpenObserve organization, with a five-minute query window that includes the request.

### Artifact

The backend's response, structured request log, and [SLI-01](../../observability.md#sli-01) histogram.

### Response

The operator shall use the response's `x-request-id` to find the request's log point, read its route, failure outcome, and duration, and see a numeric P95 in the `server_error` series.

### Response Measure

Within five seconds of the failed response, a query of the staging organization returns its log point with the request ID, route, and failure outcome. Within one minute, the [SLI-01](../../observability.md#sli-01) query returns a numeric P95 for that route's `server_error` series.

## QRT-01

The staging deployment exposes a failed core-task request's log point and P95 failure series within the required windows.

- **Status:** Active
- **Level:** deployed
- **Runs at:** the staging deployment on the university VM: `python3 scripts/check-sli.py --staging-url $STAGING_URL --env-file ~/cards/staging.env`. The script queries `$OPENOBSERVE_URL` and reads [SLI-01](../../observability.md#sli-01) in the staging organization.

### Procedure

1. Deploy the tested commit to staging. Record the checkout commit and verify the staging backend was rebuilt from it. Use a verified staging learner account; the script prompts for its credentials without printing or saving them.
2. Run `scripts/check-sli.py` from the VM checkout. It creates a temporary German text, marks one word, and sends a generation request with an invalid browser-provider result. The backend returns HTTP 502 without calling an external LLM. The script deletes its temporary text and any deck it created after the check.
3. The script polls the staging `http_requests` stream for the response's `x-request-id`, route `/api/texts/{text_id}/generate`, `server_error` outcome, status 502, and numeric duration. It checks that this route's failure histogram count increased, then polls the exact [SLI-01 query](../../observability.md#sli-01) for a numeric P95.
4. In the staging SLI-01 dashboard, confirm a separate generation-route `server_error` series with a numeric P95. Search the production organization for the same request ID and confirm no result. Send no test traffic to production.
5. Record the date, deployed commit, staging environment, request ID, first-seen times, P95 value, query output, sanitized dashboard screenshot, and verdict in the [testing plan](../../project-plan.md#quality-requirement-testing-plan).

**Pass when:** the matching staging log point is queryable within five seconds of the failed response and the staging SLI-01 query returns a numeric `server_error` P95 for the generation route within one minute; the request ID is absent from production.
