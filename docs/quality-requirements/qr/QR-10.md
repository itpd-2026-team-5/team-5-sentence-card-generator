# QR-10: Diagnose A Failed Request

An operator can locate a failed staging request and its aggregate latency signal.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** Medium
- **Technical risk:** Medium

## Scenario

### Source

A system operator investigating a failed request.

### Stimulus

A staging request returns a server error while telemetry is enabled.

### Environment

The deployed staging backend and staging OpenObserve organization, with a five-minute query window that includes the request.

### Artifact

The backend's response, structured request log, and [SLI-01](../../observability.md#sli-01) histogram.

### Response

The operator shall use the response's `x-request-id` to find the request's log point, read its route, failure outcome, and duration, and see a numeric P95 in the `server_error` series.

### Response Measure

The matching log point and P95 series are queryable within 30 seconds of the failed response.

## QRT-01

**Type:** deployed.

With staging telemetry enabled, cause one controlled staging request to fail with status 500, save its `x-request-id` and response time, and query the staging `http_requests` stream by that ID. Check `route`, `outcome=server_error`, and numeric `duration_ms`. Run the exact [SLI-01 query](../../observability.md#sli-01) over the surrounding five minutes and confirm a numeric failure series within 30 seconds. Check the production organization has no test request. Record the date, commit, environment, result, and sanitized screenshots in the [testing plan](../../project-plan.md#quality-requirement-testing-plan). This test has not yet run on the VM.
