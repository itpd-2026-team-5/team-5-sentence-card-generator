# ADR-001: One Frontend, One Backend, And A PostgreSQL Database

- **Status:** Accepted
- **Created:** 2026-10-24
- **Updated:** 2026-10-24
- **Containers:** `frontend`, `backend`, `database`
- **Addresses:** [`FR-001`](../../functional-requirements/fr/FR-001.md), [`FR-003`](../../functional-requirements/fr/FR-003.md), [`FR-009`](../../functional-requirements/fr/FR-009.md), [`FR-011`](../../functional-requirements/fr/FR-011.md), [`QR-02`](../../quality-requirements/qr/QR-02.md), [`QR-04`](../../quality-requirements/qr/QR-04.md)
- **Decision:** [`DEC-006`](../../decisions.md#dec-006), [`DEC-023`](../../decisions.md#dec-023)

## Context

The product has to run as a web application in Chrome and Firefox ([`CON-02`](../../product-vision.md#con-02)), be built by four students in one semester ([`CON-04`](../../product-vision.md#con-04)), keep each learner's texts, decks, cards, and review history, and let a teacher see only the decks shared with them.
Card generation calls an LLM that takes 10 to 30 seconds per request, and review scheduling must run the same way for every learner ([`CON-05`](../../product-vision.md#con-05)).
The Customer chose React and Python with FastAPI in [`DEC-006`](../../decisions.md#dec-006); the team filled in the rest of the stack in [`DEC-023`](../../decisions.md#dec-023).
This record decides how the product is split into containers and on what each runs.

## Considered Options

- **A single-page `frontend`, a `backend` API, and a `database`.**
  The browser runs the interface, the backend owns the rules and the LLM calls, and PostgreSQL keeps the data with real foreign keys.
- **A browser-only application that stores everything locally.**
  The cheapest to host, but a teacher could never see a learner's deck, and a learner's cards would be lost with their browser data.
- **A server-rendered application in one container.**
  One process is simpler, but the Customer asked for React, and the study screen needs instant reactions that a page reload per rating cannot give.
- **SQLite in place of PostgreSQL.**
  No database container to run, but concurrent writes from several learners are weaker, and the tests already run on SQLite while the product needs the real foreign keys and migrations PostgreSQL gives.

## Decision Outcome

Chosen option: a single-page `frontend` in React and TypeScript on Vite, a `backend` in Python with FastAPI, SQLAlchemy, and Alembic, and a `database` in PostgreSQL, all started by docker compose.
The `backend` is the only container that reads or writes the `database`, and the only one that holds the service's LLM key and sends email.
It beats the browser-only option because sharing with a teacher needs a server, and the one-container option because it is what the Customer chose and what the study screen needs.

## Consequences

- **Maintainability:** the backend's rules live in plain Python modules tested with SQLite and a fake LLM, and the frontend is type-checked on every build, which is what [`QR-02`](../../quality-requirements/qr/QR-02.md) checks.
- **Performance Efficiency:** each generation request is one call from the frontend to the backend that waits for the LLM, so its time is bounded by the provider; [`QR-04`](../../quality-requirements/qr/QR-04.md) sets the bound the learner may wait.
- **Cost:** three containers to run, and the API between the frontend and the backend has to be kept in step by hand, since the TypeScript types are written, not generated.
